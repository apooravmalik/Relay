Four integrated scenarios — and their safe failure paths

The outcome is either a verified new workspace state, or both original states remain intact.

FlowWhat happensWhen it fails
1. Set up Mac → VMNow relay push uses the registered VM workspace and a private SSH/Tailscale connection.Fail safe: unreachable VM, bad credentials, upload or hash failure leaves the Mac unchanged; the VM does not become the new owner.
2. PWA → Codex → MobileNow the phone reaches the PWA privately; the PWA runs Codex inside the chosen VM workspace and reports output/files back.Fail safe: phone off Tailnet or VM down means no chat connection; saved VM state remains on disk. A chat may stop only its own active Codex turn.
3. VM → MacNow Git delta pull; a one-time full export has proven the non-Git VM-only workspace case.Fail safe: changed base or patch conflict does not apply. Full export only targets a new/empty Mac folder; it never guesses a merge or deletes local files.
4. Mac → VMNow Git state, patches and non-ignored untracked files can be sent from the Mac.Fail safe: if the VM workspace changed after the handoff, Relay must surface conflict instead of overwriting cloud work.
Phone requests a Mac syncNext a small VM job service records a workspace-ID-only request; the Mac Agent checks outward through Tailnet and performs the local transfer.Fail safe: sleeping/offline Mac keeps the job queued. The PWA and Codex never receive arbitrary Mac shell access or filesystem paths.
Non-negotiable rule: exactly one side owns a writable workspace at a time. A hash-verified handoff changes ownership; a failed transfer changes nothing.
What is proven today

Private phone control of the VM, Codex work on the VM, Tailnet-only preview URLs, Mac-initiated Git handoffs, and a complete non-Git workspace export to a new Mac directory.
