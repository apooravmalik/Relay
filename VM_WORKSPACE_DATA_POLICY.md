# Workspace data and transfer policy

This document supersedes the file-selection and secret-blocking parts of sections 6–7 of `VM_WORKSPACE_PULL_IMPLEMENTATION.md`. Relay's goal is to move a usable development workspace between the user's PC and VM, including private configuration and user-created data, without assuming that Git ignore rules identify disposable files.

## Current policy

- Include ordinary files by default, including files ignored by Git: source, hidden files, lockfiles, build output, `.env` files, certificates and private keys, SQLite databases and sidecars, SQL Server `.bak` files and other backups. Do not block a file or history because it matches a secret pattern. Do not print file contents.
- Omit directories named `.git`, `node_modules`, `.venv`, `venv`, `__pycache__`, or `.cache` at any depth. `.git` is reconstructed for supported Git imports instead of copied. Preserve other directories named `build` and `dist`, as these may contain user artifacts. Rules are deliberately small and based on directory names, not file extensions. The preview lists omitted directories.
- If a current Git index contains a tracked file inside an omitted dependency or cache directory, first import fails instead of reporting exact index restoration while silently removing that file. Reachable Git history can itself contain earlier versions of excluded directories; history is not rewritten.
- First import on the PC includes Git-ignored files. The current Git-only PC-to-VM `push` also includes ignored untracked files, apart from the above dependency and cache directories. It still requires an existing commit. The legacy patch-based `pull --project` is a Git delta and does not include ignored-file changes. Initial pull creates a new directory; updating an existing project, first push of plain/unborn folders, and a bidirectional ignored-file update protocol remain future work.
- Private content travels over SSH and is staged in owner-only directories; project file permission bits are preserved on first import, without copying ownership or special mode bits. VM exports persist under `~/.relay-v0/exports` and may contain private data; expiry and quota enforcement remain unimplemented. Git config, remote credentials, hooks, stashes and other branches are not copied as Git metadata.
- Symlinks, nested repositories, submodules, Git LFS, Git attributes and certain complex Git states remain unsupported. Runtime services, installed dependencies, environment variable values not stored in the workspace, files outside the workspace and container volumes are not automatically captured or recreated.

A directory name alone cannot prove its contents are disposable. In particular, files deliberately stored inside `build`, `dist`, or Git-ignored paths remain included; users should not put unique data under the currently excluded dependency/cache directories. A later policy should allow explicit per-project inclusion/exclusion and show a detailed preview without weakening the no-overwrite guarantee.

## Database consistency

A byte-identical file transfer does not by itself establish a consistent backup of a running database. Pause independent writers for the workspace capture. For SQLite, close connections cleanly or create a consistent backup using the SQLite Online Backup API or `VACUUM INTO`; Relay currently copies files and does not automatically run either method. SQLite notes that a WAL can contain committed state and must remain paired with its database, and copying while a transaction is active can lead to corruption ([SQLite WAL documentation](https://www.sqlite.org/wal.html), [SQLite corruption guidance](https://www.sqlite.org/howtocorrupt.html), [SQLite backup API](https://www.sqlite.org/backup.html)). Relay includes SQLite sidecar files rather than applying a suffix exclusion, but its file-by-file capture cannot prove a live database is consistent.

A completed SQL Server `.bak` inside the workspace is an ordinary transferable file. Creating it and restoring it on the destination require SQL Server tooling and a compatible server; Relay does not do these operations. Microsoft documents the backup/restore workflow and states that a backup cannot be restored to an older SQL Server version ([Microsoft backup and restore](https://learn.microsoft.com/en-us/sql/relational-databases/backup-restore/quickstart-backup-restore-database?view=sql-server-ver16), [version compatibility](https://learn.microsoft.com/en-us/troubleshoot/sql/database-engine/backup-restore/backup-restore-operations)). A service's data outside the workspace, such as a Docker named volume, requires a separate database-aware export or volume workflow ([Docker volumes](https://docs.docker.com/engine/storage/volumes/)).

## Research basis and next steps

Git says `.gitignore` identifies intentionally untracked files, not disposable files, so it is not a workspace-transfer policy ([Git documentation](https://git-scm.com/docs/gitignore)). npm documents rebuilding `node_modules` from a matching lockfile with `npm ci`, and Python documents that virtual environments generally contain absolute paths and should be recreated when moved ([npm ci](https://docs.npmjs.com/cli/commands/npm-ci/), [Python venv](https://docs.python.org/3.11/library/venv.html)). Preserve lockfiles and manifests; do not automatically execute installation scripts.

Next work should add database-aware SQLite snapshots, SQL Server backup/restore handoffs, selected external data roots and container-volume exports; safe updates for an already imported destination; plain/unborn PC-to-VM imports; clear preview overrides; and bounded, secure export retention. These require separate protocols and tests; copying a file today does not implement them.
